# 调试报告

## 概述

长对话调试结束后，关键信息散落在上百k的上下文里。直接总结容易只给结论、跳过失败方向、丢失中间推理链。

**核心原则：** 一份好的调试报告必须让没参与调试的人也能完整理解"为什么是这个根因"——包括排除了什么、为什么排除。

## 何时使用

- 调试接近尾声，准备总结
- 用户要求输出调试报告 / 调试总结
- Bug 修复完成后归档

## 报告必须覆盖的内容

回溯整个对话上下文，确保报告包含以下要素：

1. **问题是什么** — 用户最初报告的现象、影响范围、复现条件
2. **调查了哪些方向** — 按时间顺序，列出每个尝试过的方向，包括做了什么、发现了什么、得出什么结论
3. **失败的方向** — 哪些路走不通，为什么排除（具体证据，不是"排除了 X"）
4. **根因** — 根本原因是什么，产生机制是什么
5. **修复** — 改了什么，为什么这样改
6. **验证** — 如何确认修复有效

## 写作要求

- **回溯上下文**：内容必须来自对话中的实际操作和发现，不要编造
- **保留失败路径**：失败方向是报告的核心价值，不要省略
- **具体**：写文件名、函数名、行号、具体值，不要写"某个文件"
- **因果链完整**：读者能从现象一路跟到根因，中间没有逻辑跳跃
- **摘录核心代码**：在关键节点贴出相关代码片段（问题代码、修复代码、关键数据流经过的函数签名或调用链），让读者不用翻源码就能理解问题所在
