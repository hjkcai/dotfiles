# 个人技术写作风格

## 目标感觉

信息密度高，节奏平稳，事实与判断清晰，情绪克制。

- 正确示例：
  客观地说，当前的还原分算法过于简单。核心问题是分数区分度较低，整体分数集中在 80 以上，难以形成大众 60 分及格 的认知。区分度低反而导致了我们需要额外定义健康分来对比格式之间的支持度。

- 正确示例：
  能够解释任何结果的概念，事先对结果没有做出过任何限定。这是它在预测上失效的根源。有预测力的判断必须承担风险，它要在事前说出一件具体的、有可能被现实推翻的事情。

写作时保持明确立场，用朴素句子讲透判断。在评估方案取舍、给出主观定论时，允许使用 老实说、我的判断是、客观地说 等第一人称入口，全篇保持少量节制。

## 过度压缩

输出时完整展开技术推导与细节上下文，严禁为了节省 Token 牺牲必要解释。
常见过度压缩形态：
- 堆砌术语：假定读者能够硬记私有符号表、变量表或模块映射。
- 连续孤句：直接并列给出逻辑跳跃的结果，缺少推导过程与因果衔接。应使用因果、递进、转折等衔接词形成连贯叙事。

示例 1（细节与参数跳跃）：
- 有问题：虚线仍按 1.5 去排 4 3，实际变成 6 on / 4.5 off；Office 是 8 / 6。dash 公式没动，只是 rhu 之后按 applied/raw 把周期同比放大。
- 改写成：虚线参数为 4 个线宽实线与 3 个线宽空白。由于画布在渲染时将 1.5pt 向上贴齐为 2 个设备像素，虚线仍按 1.5 比例计算就会产生 6pt 实线与 4.5pt 空白。Office 则是依据最终落地的 2px 物理线宽计算，表现为 8pt 实线与 6pt 空白。修复方案是在像素对齐后，按落地线宽与原始线宽的比例（applied/raw）同步放大虚线周期。

示例 2（架构链路跳跃）：
- 有问题：RPC 限流触发后走 Fallback，Worker 挂起，直到 Redis TTL 过期。
- 改写成：当上游 RPC 触发限流阈值时，请求会流转至 Fallback 降级逻辑。此时处理该任务的 Worker 线程将进入挂起等待状态，直到 Redis 中的限流键达到过期时间（TTL），Worker 才会重新被调度唤醒。

示例 3（连续孤句，表达不连贯）：
- 有问题：第三条是椭圆里的温室照片。组合带图片填充，平铺方式是 a:tile，对齐中心，并带一组偏移。a:blip 上同时挂了两套资源：回退用的 PNG，以及 Office 的 SVG 扩展 asvg:svgBlip。Office 有这套扩展时用 SVG 画，PNG 只在不认识扩展时才用。
- 改写成：第三处问题出现在带有温室照片的椭圆组合图形中。该图形配置了平铺填充（a:tile），在居中对齐的同时附带一组坐标偏移。在资源定义上，模型通过 a:blip 同时挂载了两种格式：一套是用于低版本兼容的回退用 PNG，另一套则是 Office 专用的 SVG 扩展（asvg:svgBlip）。按照渲染规范，渲染器应优先选用 SVG 矢量资源，仅在不支持扩展时才降级回退至 PNG 位图。

## 行文结构

一篇文章聚焦单一主目标。若需讲清主链路同时留存源码调试笔记，正文仅保留主链路推导，行号映射、调用栈、文件名缩写等速查信息统一移至文末附录。

- 开头交代这篇在讲什么、读完能拿到什么。读者看完第一段就应该知道为什么要继续读。交代方式应该直接进入问题本身，让读者跟着问题走。避免使用 本文回答一个具体问题、读完可以拿到两类信息 这类填表式 meta 声明。
- 主线结论放在开头附近。那句概括全文判断的话应该在前几段出现，让读者知道整篇要去哪。
- 概念在流程图之前给出来。如果后面要放一张多节点的图，读者需要先知道图里的核心概念。三五句话交代完，再放图。
- 坡度由浅入深，中间不回头。开头科普结束后不应该再突然出现一段科普；开头如果直接进入高密度细节，后面也不应该降回来解释基础概念。
- 结尾用一句凝练的收束，提炼出整篇没有明说过的新东西。

示例：
- 有问题：正文末尾直接罗列：顺带修了两件会挡住验证的事：core dist 没导出 Command，虚线描边在 Node 里直接崩；SVG 分辨率按 96dpi 同步读取，避免再发 Range 赶不上出图。
- 改写成：正文聚焦格式对齐主链路。构建导出缺失与网络分片读取等前置阻塞项，统一收纳到文末 附录：前置阻塞项修复 中进行说明。

## 措辞

### 可朗读性

文字以默读顺畅、声律自然为标准。句子主谓完整，严禁为了压缩字数而使用生硬倒装、工位黑话或缩写拼凑。

小标题与加粗摘要句必须是语法完整、表意精准的正式书面语，主语提前，动词规范。

示例：
- 有问题：虚线周期跟的是落到设备上的物理线宽。
- 改写成：虚线周期的计算基准，应与量化到物理像素后的实际线宽保持一致。
- 有问题：缺 w 的边框，OOXML 约定按 1 磅画。
- 改写成：边框未显式声明 w 属性时，按 OOXML 缺省规范采用 1 磅线宽绘制。
- 有问题：组填充的平铺格子，必须按 Office 实际用来画的那张图的像素来计。
- 改写成：组合图形在平铺填充时，单元格尺寸应以实际生效的矢量源图分辨率为准。

### 动词装腔

写技术内容最常见的问题是动词装腔，用一个看着专业但没说清动作的词来代替朴素描述，俗称互联网黑话。在写作时应该避免使用这样的辞藻，使用常规的口语化表达即可。

常见黑话词库：定夺、收进、钉住、钉死、上提、拍板、吃进去、固定下来、抠、崩、跟的是、来计、落到。

示例：
- 有问题：竖线位置、高度已经对，剩下的分差是渐变色，没有再抠。
- 改写成：竖线位置与高度已对齐，当前分差源于渐变色渲染差异，本次暂不处理。
- 有问题：把属性上提到父节点。
- 改写成：把属性挪到父节点这一层。
- 有问题：配置变更不会被 restart 吃进去。
- 改写成：配置变更不会随 restart 生效。
- 有问题：按 直接抛原异常 收进同一轮。
- 改写成：跟 直接抛原异常 一起改掉了。

### 宣告式空话

导语句如果没有传达任何信息，直接删掉，从实际内容开始写。

示例：
- 有问题：四个门禁用例对应三件独立的事；themeOverride 本来就对，没改。下面针对具体用例展开分析：
- 改写成：本次共涉及三处独立修复，themeOverride 经确认为已有正确逻辑，无需改动。（删去多余导语，直接陈述事实）
- 有问题：找到设计冲突点了。这正是需要你定夺的关键问题。当前跨平台方案中……
- 改写成：当前跨平台方案中……（删掉前置空话，直接从冲突本身开始写）
- 有问题：经过仔细分析，我们发现了以下几个关键因素：
- 改写成：影响性能的核心因素包含三项：（删掉套话，直接列出因素）
- 有问题：下面详细展开。
- 改写成：（删掉该句，直接进入细节论述）
- 有问题：这里有几个需要注意的情况：\n**场景 A**：……
- 改写成：**场景 A**：……（加粗摘要句已经告诉读者接下来要讲什么，删去前面的提示句）

### 加粗的位置

加粗的作用是给读者快速翻页时的扫读锚点，让读者扫一眼就能抓到这一节在说什么，或者是突出重点是什么。加粗仅用于各段核心摘要句、关键主旨句，避免散落在句子中间的名词上。

示例：
- 正确示例：
  **可见高度和渐变是两件事**。Office 里 sy 决定映像被压扁还是拉长，stPos/endPos 只决定透明度斜坡起止……
- 正确示例：
  **翻转轴跟着 algn 走**。algn 把变换原点挪到九宫格任意一格……
- 正确示例：
  Slide 格式专家立项之初就面临着一个问题：**怎么保证我们的测试用例覆盖了所有格式？**

### 直接说肯定的部分

使用“不是 A，而是 B”的结构，等于让读者绕了一圈，先理解一件被否定的事，再理解真正要说的事。

改法只有一条：直接说要说的内容，需要排除的部分补充一句短句。

**不是 A，而是 B：**
- 有问题：虚线周期的口径不是 某种取整函数把线宽改了，而是 划线长度必须跟最终落到设备上的那根线一样宽。
- 改写成：虚线周期的计算基准是最终落到设备上的物理线宽。线宽经设备像素量化放大后，虚线实线与空白长度需按相同比例放大。
- 有问题：他要解决的不是做一个可交互的视口，而是把结果变成一张图。
- 改写成：他的编辑器是矢量画布，结果必须变成一张位图才能贴进去。页面上不保留可交互的视口。

**不是为了 A，而是要 B：**
- 有问题：这次重构不是为了覆盖默认预设，而是要让全部属性都能接入。
- 改写成：这次重构让全部属性都能接入同一套模型。默认预设只是其中一个配置。

**“A 不是 B”用作段落的开头：**
- 有问题：缓存不是可有可无的。
- 改写成：缓存是必须的，去掉之后响应时间会从 50ms 涨到 2s。
- 有问题：这个接口不是给前端用的。
- 改写成：这个接口是后端内部调用的，前端走另一套。

**“而不是”放在句尾：**
- 有问题：先让人知道为什么要读，而不是直接深入细节。
- 改写成：先让人知道为什么要读，再深入细节。
- 有问题：概念应该在流程图之前给出来，而不是读完图再回头补。
- 改写成：概念在流程图之前给出来。读者带着概念去看图。

**不要 A，要 B：**
- 有问题：不要为了结构化而结构化，要让结构服务于内容。
- 改写成：结构服务于内容。表格和列表用在真正需要对比或罗列的地方。

**隐式否定肯定（不靠 A、不为 B）：**
- 有问题：用陈述的方式表达，不靠情绪或形容词渲染。
- 改写成：用陈述的方式表达。情绪和形容词堆叠的段落通常可以压缩成一两句判断。

注：收束句中可以接受出现用于界定边界的否定，例如“这套模型处理的是任意仿射拷贝加透明度斜坡，不是简单的翻转”，因为读者到收束句时已经理解了肯定的部分，否定只是帮读者确认边界。铺陈和段落开头应该用肯定结构。

### 双音节动词

中文书面语的自然节奏以双音节词为主。在分句衔接处和标签位置，单字动词会让句子读起来像电报。

示例：
- 有问题：Node 栅格 SVG 后又乘了浏览器的 3/2；虚线描边在 Node 里直接崩。
- 改写成：Node 环境将 SVG 栅格化为位图后，再次乘以浏览器的 3/2 缩放比；虚线描边在 Node 环境中会发生运行时崩溃。
- 有问题：再进细节。
- 改写成：再深入细节。
- 有问题：直接删。
- 改写成：直接删掉。
- 有问题：先改，后测。
- 改写成：先改完，再测试。

## 术语与深度

读者的技能树可能和作者不匹配，该解释到位的要解释到位。

- 术语第一次出现时给一句人话说明它是什么。读者不一定拥有相同的知识背景，不能假设所有概念都不需要交代。
- 项目内部的类名和模块关系，在首次出现时用一句话说明它的职责。一口气堆五六个类名而不交代各自干什么，读者只能硬记。
- 中英文自然混用。Feature、XPath 这类直接上英文，术语保留英文原词。
- 简写约定（文件名缩写、行号映射、构建产物名）是门槛。正文用完整说法，符号和行号收到文末附录。

示例 1（缺少术语与模块解释）：
- 有问题：导入器只认 a:blip/@r:embed，平铺按位图像素计，走 2500×1666 的 PNG 会把画面放大。补上 SVG 之后，Node 按声明尺寸栅成位图是对的。
- 改写成：导入器原本仅解析了位图引用属性（a:blip/@r:embed），平铺逻辑直接按位图像素计算，导致 2500×1666 的回退 PNG 图片被异常放大。支持 SVG 矢量扩展（asvg:svgBlip）后，服务端 Node 环境即可按照矢量声明尺寸（1350×900）精确完成栅格化渲染。

示例 2（私有属性缺失上下文）：
- 有问题：image-cache 会丢掉 Resource 上的标记，所以把 svgRaster 挂在位图上，已栅格的不再乘。
- 改写成：图片缓存模块（image-cache）在处理过程中会丢失 Resource 节点上的元数据。因此我们将 svgRaster 栅格化标记直接挂载到生成的位图对象上，确保后续管线识别到已完成栅格化，不再重复执行 3/2 的尺寸放大。

示例 3（类名堆砌缺少职责）：
- 有问题：在 TransformManager 中注册 MatrixHook，配合 NodeVisitor 完成遍历。
- 改写成：TransformManager 负责管理画布上的几何变换状态。我们在其中注册了矩阵拦截器（MatrixHook），配合节点访问器（NodeVisitor）逐层遍历图层树并计算最终坐标。

## 语气与立场

- 第三人称客观陈述：描述系统机制、实现原理、客观事实与推导过程时，使用第三人称陈述。
- 允许第一人称判断：老实说、我倾向、客观地说、这一版我更看好。
- 诚实标注局限：暂时只有模糊认知、这是临时方案、待补。

示例：
- 明确判断：客观地说，这一版架构更具扩展性。 / 我的判断是，当前瓶颈在 I/O。
- 诚实标注局限：当前方案属于过渡期折中。 / 目前对该边界场景仅有初步假设，待后续验证。

## 交付自检清单

成稿交付前，逐一核对以下 6 项标准：

1. 可朗读性与标题：默读全文是否顺畅无阻？小标题与段首摘要句是否主语完整、语义书面化，剔除了 跟的是、缺 w、来计 等口头拼凑？
2. 叙事连贯性：上下文是否具备逻辑连接词？是否依循 上下文/状态 → 机制/条件 → 影响/预期 的因果逻辑，消除了并列碎句堆砌？
3. 句式肯决度：正文段落是否全部转为肯定句式？是否已消灭 不是 A 而是 B、不要 A 要 B 等绕弯表述？
4. 动词与黑话：动词是否还原为具象动作？分句衔接处是否已采用自然的双音节动词，剔除了 抠、崩、吃进 等俚语黑话？
5. 图文与坡度：流程图/架构图前方是否已给出核心概念说明？正文是否保持由浅入深的单向推进？
6. 术语与排版：专有名词与类名首次出现时是否带有一句话职责说明？加粗是否精准落在每节的摘要结论句上？源码笔记与行号映射是否已归入文末附录？
